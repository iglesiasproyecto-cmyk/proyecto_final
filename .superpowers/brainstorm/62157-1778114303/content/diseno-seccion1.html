🏗️ Descomposición en sub-proyectos (orden de ejecución)

SP-1 — Corrección de bugs críticos
Bloquea todo lo demás. Primero esto.
  • 403 en mutaciones geografía (RLS faltante)
  • 400 en lista de usuarios enriquecida
  • Creación de tareas rota (auth_user_id desvinculado)
  • Mock mode con sesión expirada → loop infinito
SP-2 — Multi-tenancy + RLS estricta
Core del SaaS. JWT Claims + políticas por rol.
  • Trigger set_tenant_claims() en login/cambio de rol
  • Funciones SQL: get_my_tenant_id(), is_super_admin(), get_my_ministerios()
  • RLS estricta por tabla y por rol
  • Mecanismo de invalidación de caché JWT
SP-3 — Migración de esquema
Ajustes al schema para SaaS + cursos mixtos.
  • curso: id_ministerio nullable + agregar id_iglesia
  • tarea: agregar id_sede y id_ministerio explícito
  • evento: verificar FK de sede/ministerio
  • Índices de performance en columnas tenant
SP-4 — CRUDs completos por rol
UI completa para cada rol con permisos correctos.
  • Admin iglesia: gestionar sedes, ministerios, miembros, pastores asignados
  • Lider: gestionar su ministerio completo
  • Servidor: vista personal (tareas, eventos, aula)
  • Superadmin: administradores de iglesia (nuevo CRUD)
SP-5 — Aula de Formación multi-nivel
Cursos de iglesia (todos los miembros) y cursos de ministerio (solo ese ministerio).
  • Cursos de iglesia: admin crea, todos los miembros los ven
  • Cursos de ministerio: líder crea, solo miembros del ministerio
  • RLS scoped al nivel correcto
  • UI diferenciada por tipo de curso

🔐 Arquitectura JWT Claims + Cache Management

Flujo completo: Login → Claims → RLS → Cache Refresh
📥 Al hacer login:
JWT app_metadata: {
  tenant_id: 5,        // id_iglesia
  role: "admin_iglesia",
  claims_at: 1746000000 // timestamp
}
🔄 Cuando cambia rol/iglesia:
1. DB actualiza usuario_rol
2. Trigger llama update_user_claims()
3. Actualiza app_metadata via service role
4. Frontend detecta claims_at stale
5. Llama supabase.auth.refreshSession()
6. Nuevo JWT con claims actualizados ✅
⚡ Estrategia de caché:
• claims_at en JWT vs permissions_updated_at en tabla usuario_rol
• AppContext compara en cada carga → si DB.updated_at > claims_at → fuerza refresh automático
• JWT expira en 1 hora por defecto → máximo 1h de claims stale en el peor caso
• Para cambios críticos (desactivar usuario): usar supabase.auth.admin.signOut(userId)
