Enfoques para Multi-Tenancy SaaS

La decisión más crítica: ¿cómo aislar los datos de cada iglesia? Elige un enfoque antes de continuar.

A

JWT Claims + RLS estricta

Al hacer login, se guarda en el token JWT: { tenant_id: id_iglesia, role: "admin_iglesia", ministerio_ids: [1,2] }. Las políticas RLS leen directamente del token — sin consultas extra a la DB.

Pros

  • Más rápido (0 joins en RLS)
  • Enfoque oficial Supabase para SaaS
  • Sin cambios de esquema grandes

Contras

  • Si cambia el rol, hay que refrescar el token
  • Requiere Edge Function o trigger para poblar claims
B

Funciones SQL SECURITY DEFINER

RLS llama a funciones como get_my_tenant_id(), is_admin_of_iglesia(x), get_my_ministerios() que consultan la DB en cada verificación de fila.

Pros

  • Permisos siempre actualizados en tiempo real
  • Sin lógica de claims/token
  • Ya tienes funciones parciales en el proyecto

Contras

  • Más lento (consulta DB por cada fila)
  • Puede ser problemático con tablas grandes
C

Híbrido (Recomendado ★)

JWT Claims para las verificaciones simples y frecuentes (tenant_id, role). Funciones SQL para reglas complejas (¿es lider de este ministerio específico?). Lo mejor de los dos mundos.

Pros

  • Rápido en el 90% de los casos (JWT)
  • Flexible para reglas complejas (SQL)
  • Escalable a producción real
  • Patrón usado por Supabase en sus guías SaaS

Contras

  • Más complejo de implementar inicialmente
  • Requiere trigger para sincronizar claims

¿Cómo funciona el Híbrido en la práctica?

Flujo de autenticación SaaS
1. Usuario hace login → Supabase Auth emite JWT
2. Trigger on_auth_user_login → llama RPC set_tenant_claims()
3. Claims en JWT: { app_metadata: { tenant_id: 5, role: "admin_iglesia" } }
4. RLS simple: WHERE id_iglesia = (jwt → 'app_metadata' → 'tenant_id')::int
5. RLS compleja (lider): WHERE id_ministerio IN (SELECT get_my_ministerios())
✅ Superadmin: claim especial role: "super_admin" → bypass RLS vía USING (is_super_admin())
